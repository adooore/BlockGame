### 1. 项目总览（Overview）

- **游戏简介**
  - 方块动作 / 解谜向游戏，目前已包含至少以下模式：
    - 颜色收集（Color Collect）
    - 危险通道（Dangerous Passage）
    - 红线（Red Line）

  - `dist/gameColorCollect.html`：颜色收集模式运行页面，负责：
    - 页面样式与赛博风 UI
    - 引入核心 JS 模块（`gameData.js`、`gridSystem.js`、`waveSystem.js`、`frameScheduler.js`、`player.js` 等）
    - HUD / 计时 / 颜色指示器等 UI 元素
- **关键前端脚本模块（dist/js）**
  - `gameData.js`：关卡与游戏数据（关卡配置、颜色目标等，具体结构待进一步整理）。
  - `gridSystem.js`：网格 / 地图系统，负责方块布局与坐标相关逻辑（待补充细节）。
  - `waveSystem.js`：波次 / 刷新机制，控制关卡中方块的生成与推进节奏（待补充）。
  - `frameScheduler.js`：统一帧调度器，负责解耦逻辑更新与渲染帧率（详见后文「特殊处理 / Hack 说明」）。
  - `player.js`：玩家控制与运动逻辑（移动、跳跃、碰撞等，待进一步总结）。
  - 其它模块如 `controllerManager.js`、`soundManager.js`、`pauseMenu.js`、`gameWebSocket.js`、`debugPanel.js` 等分别负责输入、音效、暂停菜单、联机/调试等功能。

### 2. 核心设计原则（Design Principles）

- **抽象优先级最高（本项目最高优先级）**
  - 在功能可用的前提下，优先保证抽象层次清晰、单一职责明确、配置单一来源（Single Source of Truth）。
  - 出现“同一语义参数在多个模块重复定义”的情况时，默认判定为架构风险，应优先收敛到一个统一定义点。
  - 本项目不鼓励为了“兜底运行”而增加不必要的弱依赖分支；对静态依赖关系应保持显式、可失败、可快速修复。
  - 目标是避免代码随迭代逐步失控：宁可早期做抽象收敛，也不要后期在多处同步修补。

- **逻辑更新与渲染解耦**
  - 使用统一的帧调度器（`FrameScheduler`）来驱动逻辑更新与渲染：
    - 逻辑层使用固定时间步长（默认 60Hz）。
    - 渲染层固定目标 60fps。
  - 所有与「时间推进 / 速度控制」相关的逻辑，应尽量挂在调度器驱动的更新回调中，而不是各自使用 `Date.now()` / `setTimeout` 分散计算。

- **尽量数据驱动关卡**
  - 关卡表现差异尽量通过 `gameData.js` 等数据配置来体现，而不是把具体关卡逻辑写死在渲染或玩家脚本中。
  - 新增关卡 / 调整难度时，优先考虑修改数据结构而非大量改动逻辑代码。

- **性能与体感优先**
  - 避免在每一帧频繁创建临时对象或做复杂计算，尽量把重计算部分前置或分摊。
  - 对玩家体感影响较大的内容（移动速度、跳跃高度/时长、刷新节奏）要通过统一机制（如帧调度器参数）集中调整。

### 3. 模式与关卡的核心逻辑

#### 3.1 颜色收集（Color Collect）

- **模式核心目标**
  - 玩家在地图中收集指定颜色的方块，可能需要：
    - 达到一定数量的目标色方块。
    - 避免触碰某些危险颜色（例如 UI 中标出的「危险障碍」颜色）。
  - UI 中会显示：
    - 目标颜色、剩余目标数量。
    - 危险颜色（在特定关卡中启用）。
    - 用时、惩罚时间、最佳记录等指标。

- **关键模块协作（推测结构，后续可根据源码细化）**
  - `gameData.js`：定义每一关的：
    - 目标颜色 / 危险颜色
    - 需要收集的数量
    - 初始布局或生成参数
  - `gridSystem.js` / `waveSystem.js`：
    - 控制方块在网格中的生成、移动和波次节奏。
  - `player.js`：
    - 玩家移动、跳跃与碰撞检测（决定是否成功收集或死亡）。
  - `frameScheduler.js`：
    - 统一推进游戏时间（移动、刷新、跳跃动画等依赖于调度器）。

- **做新关卡时应围绕的点**
  - 明确当前关卡的「核心体验」：例如是考验操作精度、路线规划还是节奏判断。
  - 在 `gameData.js` 中配置：
    - 目标 / 危险颜色。
    - 出现顺序 / 位置 / 数量。
  - 避免在 `player.js` / `gameColorCollect.html` 里硬编码特定关卡逻辑，尽量通过数据驱动。

#### 3.2 危险通道（Dangerous Passage）

  - 本模式的失败 / 胜利条件。

### 4. 特殊处理 / Hack 说明（Tricky Parts & Hacks）

#### 4.1 统一帧调度器 `FrameScheduler`（`dist/js/frameScheduler.js`）

- **设计目的**
  - 统一控制：
    - 逻辑层固定步长更新（默认 60Hz）。
    - 渲染层目标 60fps。
  - 解决不同机器 / 不同刷新率下，游戏速度与体感不一致的问题。

- **关键机制（基于当前实现）**
  - 固定逻辑步长：
    - `fixedHz`（默认 60） → `fixedStepSec = 1 / fixedHz` → 每次更新用固定的 `dt`。
    - 单帧最大时间步长由 `maxFrameDeltaMs` 限制，避免窗口切回等极端情况导致一次性推进过多逻辑。
    - 通过 `accumulatorMs` + `while (accumulatorMs >= fixedStepMs)` 的方式累计并多次调用 `onUpdate`，但 `steps` 受 `maxCatchUpSteps` 限制。
  - 渲染节奏：
    - `renderIntervalMs = 1000 / 60`，目标 60fps。
    - 增加 `renderSlackMs` 容差，减少 60Hz 屏幕下 rAF 抖动造成的漏帧。
    - 使用 `renderAccumulatorMs` 控制何时调用 `onRender`，并在渲染后减去一个单位间隔而非清零，以避免长期偏慢。
  - 暂停与恢复：
    - `pause()`：设置 `paused = true`，在暂停状态下清空时间累积但继续请求下一帧。
    - `resume()`：重置累积与时间戳，从当前时间重新开始。

- **使用与修改注意事项**
  - 所有「与时间相关的游戏逻辑」（移动速度、重力、跳跃、动画时间等）应当基于 `onUpdate(fixedStepSec)` 中给出的 `dt` 来计算。
  - 如果觉得整体游戏「过快 / 过慢」，优先调整：
    - 玩家 / 物体的速度参数（乘以统一的速度系数）。
    - 或者调整 `fixedHz`，但需小心对所有依赖 dt 的逻辑带来的连锁影响。
  - 避免在各处再自己维护一套 `requestAnimationFrame` 或 `setInterval`，以免出现多重时间源导致的不同步问题。
